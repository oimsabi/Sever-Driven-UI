🧩 Server-Driven UI
แนวคิด เปรียบเทียบ ขั้นตอนการทำงาน JSON → UI ลองเล่น อัปเดตทันที ข้อดี/ข้อเสีย
อธิบายหลักการทำงานด้วยภาพเคลื่อนไหว

หน้าตาแอป ไม่ได้ ถูกฝังไว้ในแอป
แต่ถูก ส่งมาจากเซิร์ฟเวอร์

Server-Driven UI (SDUI) คือแนวคิดที่ให้เซิร์ฟเวอร์เป็นคนบอกว่า “หน้าจอนี้ประกอบด้วยอะไรบ้าง เรียงยังไง ข้อมูลอะไร” ในรูปแบบ JSON แล้วฝั่งไคลเอนต์ทำหน้าที่แค่ แปล JSON เป็น UI จริง เท่านั้น

01 — แนวคิด

ใครเป็นคน “ตัดสินใจ” ว่าหน้าจอหน้าตาแบบไหน?

หัวใจของเรื่องนี้มีแค่คำถามเดียว คือ ตรรกะของหน้าตา (UI logic) ถูกเก็บไว้ที่ไหน

📱

แบบดั้งเดิม — Client-Driven UI

โค้ดหน้าจอทั้งหมดถูก คอมไพล์ฝังไว้ในตัวแอป เซิร์ฟเวอร์ส่งมาแค่ “ข้อมูลดิบ”

// เซิร์ฟเวอร์ส่งมาแค่ข้อมูล
{ "name": "รองเท้าวิ่ง Aero X",
  "price": 2490,
  "discount": 20 }

// แอปเป็นคนตัดสินใจเองว่าจะวาดยังไง
Column {
  Image(product.image)
  Text(product.name)
  Text("฿" + product.price)
}
  • อยากย้ายปุ่ม → ต้อง build + ส่งขึ้น store ใหม่
  • iOS / Android / Web ต้องแก้แยกกัน 3 ที่
  • ผู้ใช้ที่ไม่อัปเดตแอป จะเห็นของเก่าตลอดไป

Server-Driven UI

เซิร์ฟเวอร์ส่ง “พิมพ์เขียวของหน้าจอ” มาด้วย แอปแค่แปลตามที่บอก

// เซิร์ฟเวอร์ส่งทั้งโครงหน้าจอ + ข้อมูล
{ "components": [
   { "type": "image",  "label": "👟" },
   { "type": "text",
     "variant": "title",
     "value": "รองเท้าวิ่ง Aero X" },
   { "type": "button",
     "tone": "primary",
     "value": "ซื้อเลย ฿2,490" }
]}
  • อยากย้ายปุ่ม → แก้ JSON บนเซิร์ฟเวอร์ จบ
  • แก้ที่เดียว ทุกแพลตฟอร์มเปลี่ยนพร้อมกัน
  • ทำ A/B test / โปรโมชันตามเทศกาลได้ทันที
สิ่งที่ยังอยู่ฝั่งแอปเสมอ: ตัว “ชิ้นส่วน UI” (component) จริง ๆ เช่นปุ่ม การ์ด รูปภาพ ยังถูกเขียนเป็นโค้ด native อยู่ในแอป — เซิร์ฟเวอร์ เลือกและจัดเรียง ชิ้นส่วนเหล่านั้น แต่ ไม่ได้ส่งโค้ดมารัน (นี่คือจุดต่างจาก WebView)

    07 — ต้องแลกกับอะไร
    
ไม่มีสถาปัตยกรรมไหนฟรี

    
SDUI แก้ปัญหาเรื่องความเร็วในการเปลี่ยนแปลง แต่ก็ย้ายความซับซ้อนไปไว้อีกที่หนึ่ง

  


  

    

      
✅ ได้อะไร

      
    
        
  • ปล่อยของเร็วมาก — เปลี่ยน UI ได้ในระดับวินาที ไม่ผูกกับรอบ release
    • 
        
  • ความสม่ำเสมอข้ามแพลตฟอร์ม — แหล่งความจริงเดียวคือ JSON
    • 
        
  • ทดลองได้ถูก — A/B test, personalization, โปรโมชันตามช่วงเวลา
    • 
        
  • ย้อนกลับง่าย — ถ้าพัง แค่ rollback config ไม่ต้อง hotfix แอป
    • 
        
  • ทีมธุรกิจ/ดีไซน์ขยับเองได้ ผ่าน CMS โดยไม่รบกวนทีมแอป
    • 
      

    

    

      
⚠️ เสียอะไร

      
    
        
  • ต้องลงทุนสร้างระบบพื้นฐาน — schema, renderer, CMS, เครื่องมือ preview
    • 
        
  • เวอร์ชันซับซ้อน — แอปเก่าต้องรอด แม้เจอ component ที่ยังไม่รู้จัก
    • 
        
  • ดีบักยากขึ้น — บั๊กอาจอยู่ใน JSON ไม่ใช่ในโค้ด
    • 
        
  • เสี่ยงพังทั้งระบบ — config ผิดตัวเดียวกระทบผู้ใช้ทุกคนทันที
    • 
        
  • ต้องพึ่งเครือข่าย — ต้องมี cache/offline fallback เสมอ
    • 
        
  • ไม่เหมาะกับหน้าจอที่ interactive สูง เช่น กล้อง แผนที่ เกม
    • 
      

    

    

      
🎯 ใช้เมื่อไหร่ถึงคุ้ม

      
    
        
  • หน้าจอที่ เปลี่ยนบ่อยตามธุรกิจ — หน้าแรก, ฟีด, หน้าโปรโมชัน, onboarding
    • 
        
  • มีหลายแพลตฟอร์มที่ต้อง เหมือนกันเป๊ะ
    • 
        
  • ทำ experiment บ่อย จนรอบ release ตามไม่ทัน
    • 
        
  • ไม่คุ้มถ้า: แอปเล็ก ทีมเดียว หน้าจอนิ่ง ปล่อยอัปเดตได้อยู่แล้ว
    • 
      

      
คำแนะนำที่ใช้กันจริง: ผสมกัน — ทำ SDUI เฉพาะหน้าจอที่เปลี่ยนบ่อย ส่วนหน้าจอ core ยังเขียน native ตามปกติ

    

  


  

    
กับดักที่ต้องออกแบบเผื่อไว้ตั้งแต่วันแรก

    

      
1. Forward compatibility
ส่ง type ที่แอปเก่าไม่รู้จัก ต้องข้ามเงียบ ๆ หรือแสดง fallback ไม่ใช่หน้าจอว่างหรือแครช

      
2. Cache & offline
เก็บ config ล่าสุดไว้ในเครื่อง เปิดแอปครั้งถัดไปวาดจาก cache ก่อน แล้วค่อยรีเฟรชเบื้องหลัง

      
3. Schema versioning
ใส่ minAppVersion / schemaVersion ให้เซิร์ฟเวอร์เลือกส่งเลย์เอาต์ที่แอปรุ่นนั้นรองรับ

      
4. Action ไม่ใช่โค้ด
ส่งเป็น {"action":"navigate","to":"/cart"} ให้แอปตีความ — อย่าส่งสคริปต์มารัน (ช่องโหว่ความปลอดภัย)

      
5. Validate ก่อน deploy
ตรวจ JSON ด้วย schema ใน CI + มีหน้า preview ให้ดูก่อน เพราะปล่อยผิดคือกระทบทุกคนทันที

      
6. วัดผลได้
ฝัง trackingId ในแต่ละ component เพื่อรู้ว่าเลย์เอาต์ไหนทำงานได้ดีกว่ากัน
