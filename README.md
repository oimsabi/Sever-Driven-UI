# เปลี่ยนหน้าจอแอปได้ในไม่กี่นาที — Server-Driven UI อธิบายด้วยภาพ

หน้าเว็บภาษาไทยที่อธิบายแนวคิด **Server-Driven UI (SDUI)** ด้วยแอนิเมชันแบบโต้ตอบได้
เขียนด้วย HTML + CSS + JavaScript ล้วน **ไม่มีไลบรารีหรือ build step**

มี 2 หน้า:

| หน้า | ไว้ทำอะไร |
|------|-----------|
| **`index.html`** | ฉบับเต็ม — แอนิเมชันทีละขั้น + แผงควบคุมให้ลองเล่นเอง |
| **`infographic.html`** | สรุป 1 หน้า เล่าด้วยภาพเป็นหลัก (ไอคอน SVG 26 แบบ วาดเอง) ข้อความรวมทั้งหน้า 85 คำ · ไม่ใช้ JavaScript เลย · สั่งพิมพ์/บันทึกเป็น PDF ได้ |

เปิดใช้งานได้ทันทีโดยดับเบิลคลิกไฟล์
(หรือรัน `python3 -m http.server` แล้วเข้า `http://localhost:8000`)

---

## ลำดับการเล่าเรื่อง

หน้านี้เล่าแบบ **เห็นผลลัพธ์ก่อน แล้วค่อยย้อนดูว่ามันแพงแค่ไหน**
เขียนให้คนที่ไม่ใช่สายเทคอ่านรู้เรื่อง ศัพท์เทคนิคถูกยกไปไว้ท้ายหน้าทั้งหมด

| # | หัวข้อ | เล่าอะไร |
|---|--------|----------|
| 00 | **ผลลัพธ์** | โชว์หน้าจอที่เสร็จแล้วก่อนเลย ไม่อธิบายอะไรนำหน้า |
| 01 | **แยกชิ้นดู** | แตะเลือกแต่ละชิ้น (รูป / ป้ายลดราคา / ชื่อ / คะแนน / ปุ่ม) แล้วชิ้นนั้นจะสว่างขึ้นในหน้าจอจำลอง ชิ้นอื่นหรี่ลง |
| 02 | **กว่าจะได้หน้าจอนี้** | เดินทีละขั้นว่าต้องผ่านมือใครบ้าง พร้อมนับเวลาสะสมจนครบ ~7 วัน และชี้ว่า 3 ขั้นสุดท้ายอยู่นอกการควบคุมของทีม |
| 03 | **ทางที่ดีกว่า** | อธิบาย SDUI ด้วยภาพ "กล่องเลโก้ + แบบแปลน" แล้วจับสองแนวทางมาแข่งกันด้วยแอนิเมชัน |
| 04 | **ลองเอง** | แผงควบคุมจริง — แก้ข้อความ/สลับสวิตช์ → กดบันทึก → กดผู้ใช้เปิดแอป แล้วเห็นจอเปลี่ยน โดยป้ายเวอร์ชันแอปไม่เคยขยับ |
| 05 | **ข้อดี / ข้อควรระวัง** | สิ่งที่ได้ สิ่งที่ต้องแลก และคุ้มเมื่อไหร่ |
| 06 | **เบื้องหลัง** (ข้ามได้) | โซนเทคนิค: แผนภาพการเดินทางของข้อมูล, การอ่านแบบแปลนทีละบรรทัดเทียบกับกล่องชิ้นส่วน, และ playground ให้เขียน JSON เอง |

คำที่ใช้แทนศัพท์เทคนิคตลอดหน้า: **กล่องเลโก้** = ชุด component ที่ compile อยู่ในแอป ·
**แบบแปลน** = JSON schema ที่เซิร์ฟเวอร์ส่งมา

## โครงสร้างไฟล์

```
index.html                    ฉบับเต็ม
infographic.html              สรุป 1 หน้า (ไม่มี JS)
assets/css/style.css          สไตล์หลัก + token + คีย์เฟรมแอนิเมชัน
assets/css/infographic.css    เลย์เอาต์ของหน้าสรุป + สไตล์สำหรับสั่งพิมพ์
assets/js/renderer.js         ตัวแปลง JSON → DOM (หัวใจของฝั่งไคลเอนต์ใน SDUI)
assets/js/main.js             ตัวควบคุมแต่ละส่วน (showcase / journey / race / flow / mapping / playground / OTA)
```

หน้าสรุปโหลด `style.css` ต่อด้วย `infographic.css` เพื่อใช้ตัวแปรสี ฟอนต์ และปุ่มร่วมกัน
จะได้ไม่ต้องประกาศ design token ซ้ำสองที่

`renderer.js` แยกออกมาโดยตั้งใจ เพราะมันคือสิ่งเดียวกับที่แอปจริงต้องเขียนเป็น native code —
ส่วนที่เหลือของหน้าเว็บเป็นแค่ "เปลือก" ที่ใช้สาธิตมันจากหลาย ๆ มุม

## Component ที่ renderer รองรับ

`text` · `button` · `image` · `badge` · `rating` · `input` · `list` · `divider` · `spacer`
· `card` · `row` · `stack`

ถ้าเจอ `type` ที่ไม่มีในทะเบียน จะแสดงกล่อง fallback แทนการแครช —
ซึ่งเป็นพฤติกรรมบังคับของระบบ SDUI จริง เพราะแอปเวอร์ชันเก่าย่อมไม่รู้จัก component ที่เพิ่งเพิ่มบนเซิร์ฟเวอร์

ตัวอย่าง schema หนึ่งหน้าจอ:

```json
{
  "screenId": "product",
  "schemaVersion": 3,
  "components": [
    { "type": "image",  "label": "👟", "height": 130 },
    { "type": "badge",  "tone": "danger", "value": "ลด 20%" },
    { "type": "text",   "variant": "title", "value": "รองเท้าวิ่ง Aero X" },
    { "type": "rating", "value": 4.5, "count": 218 },
    { "type": "button", "tone": "primary", "value": "ซื้อเลย",
      "action": { "kind": "addToCart", "id": 8823 } }
  ]
}
```

## การเปิดหน้าเว็บผ่าน GitHub Pages

เว็บอยู่ที่ **https://oimsabi.github.io/Sever-Driven-UI/**

deploy อัตโนมัติด้วย `.github/workflows/deploy-pages.yml` ทุกครั้งที่ push เข้า `main`
(หรือกด Run workflow เองจากแท็บ Actions) เว็บเป็น static ล้วนจึงไม่มีขั้นตอน build

ทุก path ในหน้าเว็บเป็น relative จึงเสิร์ฟจาก subpath `/Sever-Driven-UI/` ได้เลยโดยไม่ต้องแก้อะไร

หมายเหตุ: repo ต้องเป็น public หรือใช้บัญชี GitHub Pro ขึ้นไป และตั้ง
**Settings → Pages → Source: `GitHub Actions`** ไว้ จึงจะ deploy ได้

## แนวทาง Mobile / Tablet first

CSS เขียนแบบ mobile-first ทั้งไฟล์ — สไตล์พื้นฐานคือมือถือแนวตั้ง
แล้วค่อยเพิ่มด้วย `min-width: 640px` → `900px` → `1200px`

สิ่งที่ปรับให้มือถือเป็นหลัก ไม่ใช่แค่ย่อของเดสก์ท็อป:

| เรื่อง | ทำอะไร |
|---|---|
| **แผนภาพในหัวข้อ 06** | สร้างด้วย JS จากข้อมูลชุดเดียว แล้ววางผังใหม่ตามจอ (มือถือ = เรียงลงแนวตั้ง viewBox แคบ / จอกว้าง = เรียงแนวนอน) เดิมเป็น SVG ตายตัวกว้าง 960 พอย่อลงมือถือตัวอักษรเหลือ ~4px |
| **ลำดับการอ่าน** | บนมือถือ จอมือถือจำลองถูกตรึงไว้บนสุดในหัวข้อ 04 และ 06 และยกปุ่มควบคุมขึ้นมาชิดกัน เพื่อให้ "กดแล้วเห็นผลทันที" ไม่ต้องเลื่อนขึ้นลง |
| **พื้นที่กด** | ทุกปุ่ม/ลิงก์/สวิตช์อย่างน้อย 44×44px บนจอสัมผัส |
| **ช่องกรอก** | ใช้ฟอนต์ 16px บนอุปกรณ์สัมผัส เพื่อไม่ให้ Safari บน iOS ซูมหน้าจอเข้าเองตอนโฟกัส |
| **hover** | กฎ `:hover` ทั้งหมดอยู่ใน `@media (hover: hover) and (pointer: fine)` เพราะบนจอสัมผัสเบราว์เซอร์จะค้างสถานะ hover ไว้หลังแตะ ทำให้ปุ่มที่ไม่ได้เลือกดูเหมือนถูกเลือก |
| **แยกตามอุปกรณ์ ไม่ใช่ความกว้าง** | iPad Pro กว้าง 1024px แต่เป็นจอสัมผัส การย่อฟอร์มจึงผูกกับ `pointer: fine` ไม่ใช่ `min-width` |
| **จอเตี้ย** | มือถือ/แท็บเล็ตแนวนอน (สูง < 600px) จอจำลองเปลี่ยนเป็นแบบ "หน้าต่าง" กว้างแต่เตี้ย ไม่ยึดสัดส่วน 9:17.5 |

ทดสอบด้วย Chromium จริงที่ 375 / 390 / 640×420 / 768 / 1024 / 1440
ครบทุกขนาด: ไม่มี error, ไม่มีการเลื่อนแนวนอน, ไม่มีพื้นที่กดต่ำกว่า 44px,
ไม่มีช่องกรอกที่ทำให้ iOS ซูม, ตัวอักษรและบล็อกใน SVG ไม่ล้นกล่อง

## หมายเหตุด้านการเข้าถึง

- มีปุ่ม **แอนิเมชัน: เปิด/ปิด** บนแถบนำทาง (จำค่าไว้ใน `localStorage`)
  บนมือถือข้อความจะถูกซ่อน ไอคอนจึงสลับ 🎬 / ⏸ ตามสถานะ
- เคารพ `prefers-reduced-motion` ของระบบเป็นค่าเริ่มต้น
- รองรับจอตั้งแต่ 320px ขึ้นไป ไม่มีการเลื่อนแนวนอน
